What Is Prompt Engineering?

Prompt engineering is the practice of writing instructions for an AI model that reliably produce the output you need. It's less like programming and more like writing a very precise job description — the clearer and more structured your instructions, the more consistent and useful the AI's responses become.

A poorly written prompt might produce different formats, inconsistent categories, or irrelevant analysis. A well-engineered prompt produces the same clean JSON structure every time, with labels that actually match the review content.

The four elements of a good classification prompt:

ElementWhat it doesExample from our prompt
Role framingTells the AI who it is and what it's doing"You are a restaurant feedback analyst for Rinata..."
Defined optionsLimits the AI to a fixed set of valid values7 named categories, 3 sentiment options, 3 urgency levels
DefinitionsExplains what each option means so the AI chooses consistently"Food Quality — taste, freshness, portion size, menu items, authenticity"
Output formatSpecifies exactly what structure to return"Return ONLY valid JSON. No explanation before or after."
Why "Return ONLY valid JSON" matters:
By default, Claude likes to be conversational — it might say "Here's my analysis:" before the JSON, or add "Let me know if you'd like more detail!" after. That breaks json.loads() because the extra text isn't valid JSON. Explicitly instructing the model to return only JSON eliminates this. It's one of the most important lines in any structured-output prompt.

The Prompt We Wrote — Line by Line

Line 1 — Role:
"You are a restaurant feedback analyst for Rinata, an Italian restaurant in Minneapolis."

Lines 2-3 — Task definition:
"Your job is to read a single customer review and return a structured JSON object..."

Lines 4-12 — Category definitions:
Each category is named and described with bullet-point examples of what belongs there. This prevents ambiguity — without definitions, "the server was great" might be labeled Food Quality or Atmosphere depending on the AI's interpretation.

Lines 13-22 — Sentiment and urgency scales:
Each value is defined, not just named. "Urgency: high = serious complaint, health/safety issue, repeated failure, very angry customer." Without this definition, "high" would mean different things to the model in different contexts.

Last section — Output contract:
"Return ONLY valid JSON." followed by the exact JSON template the model must fill in. The template shows field names, types, and order — eliminating any guessing about format.

How the Code Works

Core function

categorize_review()

def categorize_review(text: str) -> dict:
    message = client.messages.create(
        model="claude-haiku-4-5-20251001",
        max_tokens=300,
        system=system_prompt,       # the prompt template
        messages=[{
            "role": "user",
            "content": f"Review:\n{text}"
        }]
    )

    raw = message.content[0].text.strip()

    # Strip markdown fences if Claude wraps in ```json ... ```
    if raw.startswith("```"):
        raw = raw.split("```")[1]
        if raw.startswith("json"):
            raw = raw[4:]
        raw = raw.strip()

    return json.loads(raw)

Breaking it down:

  • system=system_prompt — The system prompt is the persistent instruction set that applies to every message. It's separate from the user message so the AI treats it as its operating rules, not as conversational input. This is more reliable than putting everything in the user message.
  • max_tokens=300 — Caps the response length. A full JSON response for one review is about 150–200 tokens. Setting 300 gives headroom without risking a long rambling response that breaks parsing.
  • Markdown fence stripping — Even when told to return only JSON, Claude sometimes wraps the output in ```json ... ``` code fences (this is what caused the first test to fail). The stripping logic splits on the backticks and extracts just the JSON content.
  • json.loads(raw) — Converts the JSON string into a Python dictionary. After this, you access fields like result["primary_category"] instead of parsing text manually.
Batching and rate limits

Why we pause between batches

if i % BATCH_SIZE == 0:
    time.sleep(BATCH_PAUSE)   # pause 2 seconds every 10 reviews

APIs have rate limits — maximum number of requests allowed per minute. If you send 388 requests as fast as possible, the API will eventually return a 429 Too Many Requests error and stop responding.

By pausing 2 seconds every 10 reviews, we spread the load over time and stay comfortably within the limits. For 388 reviews at this pace, the total run time was about 8–10 minutes — acceptable for a one-time batch job.

Concept — Rate limiting:
Rate limits protect API servers from being overwhelmed by any single user. They're measured in requests per minute (RPM) or tokens per minute (TPM). The Anthropic free tier allows 50 RPM. Our batch approach of 10 requests per 2 seconds = 300 RPM theoretical max, but with processing time per request we stayed well under the limit.
Resilience

Incremental saving and fallback handling

# Save progress every 50 reviews
if i % 50 == 0:
    pd.DataFrame(results).to_csv(OUTPUT, index=False)

# If anything fails, use safe defaults instead of crashing
except Exception as e:
    results.append({**row_data, **FALLBACK})
    print(f"ERROR: {e}")

Two defensive patterns that protect the run:

  • Incremental saving — Every 50 reviews the current results are written to disk. If the script crashes at review 300, you don't lose everything — you pick up from the last save point. For long-running jobs this is essential.
  • Fallback on error — Instead of crashing when one review fails (bad JSON, network blip, etc.), the script logs the error and inserts a "Miscellaneous / low confidence" row so processing continues. The final CSV has 388 rows no matter what.
Concept — Defensive programming:
Writing code that handles failures gracefully rather than assuming everything will work. Real-world systems have network hiccups, API timeouts, and malformed data. Defensive code anticipates these and degrades gracefully instead of stopping cold. The two patterns above — save often, catch exceptions — are the most common forms of this in data pipelines.

The Debugging Moment — JSON Parse Failure

Debugging

Why the first test crashed

The test script sent one review to Claude and tried to parse the response with json.loads(raw). It crashed with:

JSONDecodeError: Expecting value: line 1 column 1 (char 0)

This error means json.loads() received a string that didn't start with a JSON value ({, [, a number, etc.). Instead it got a backtick — the start of a markdown code fence.

To diagnose it, we printed the raw response before parsing:

print(repr(msg.content[0].text))

Using repr() shows the string exactly as Python sees it — including escape characters. The output revealed:

'```json\n{\n  "primary_category": "Service/Staff"...\n}\n```'

Claude had wrapped the JSON in markdown code fences. The fix was to detect and strip them before parsing. This is a very common pattern when working with AI APIs — models trained on code documentation tend to format code-like output with fences even when instructed not to.

Debugging technique — repr():
print(x) shows a human-friendly version of a string. print(repr(x)) shows the raw Python representation, including quotes, escape sequences like \n (newline), and special characters. When debugging string parsing issues, repr() often reveals the problem immediately.

System Prompt vs. User Message — What's the Difference?

The Claude API (and most modern AI APIs) separates messages into two roles:

RolePurposeHow Claude treats it
SystemPersistent instructions that define behavior for the entire conversationHigh-priority operating rules — Claude follows these throughout
UserThe actual input for this specific requestThe thing to respond to, within the rules set by the system

In our script, the system message is the full prompt template (categories, definitions, output format). The user message is simply the review text. This separation is intentional:

  • The system prompt stays constant across all 388 calls — we load it once
  • Only the user message changes per review — just the review text
  • This is more efficient and more reliable than combining everything into one giant user message each time
Concept — Context window:
Every AI model has a maximum amount of text it can process at once, called the context window. By keeping the system prompt consistent and the user message short (just the review text), we use far fewer tokens per call than if we re-sent the full instructions with every review. With 388 reviews, this efficiency adds up significantly.
