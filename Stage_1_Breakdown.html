What Stage 1 Is and Why It Matters

Before writing a single line of project logic, every software project needs a working environment. Think of Stage 1 as building your workshop before you start woodworking — you need your tools laid out, your power connected, and a quick test that the lights work.

In software, that means:

  • A clean folder structure so files don't get chaotic
  • The right libraries installed so your code can use them
  • Credentials stored safely so the API accepts your requests
  • A test script that proves the whole chain works end to end

Why organize this way?

Separating code by responsibility is a core software engineering habit called Separation of Concerns. Each folder has one job:

FolderJobAnalogy
scraper/Collect raw data from GoogleThe net that catches fish
categorizer/Clean and label the dataThe processing plant
output/Store finished filesThe warehouse shelf
prompts/Hold AI prompt templatesThe recipe book

If all scripts were dumped in one folder, a project with 10+ files becomes impossible to navigate. This structure scales cleanly into Stages 2–6.

The command we ran

mkdir -p "C:\Users\shant\projects\Rinata\scraper" \
         "C:\Users\shant\projects\Rinata\categorizer" \
         "C:\Users\shant\projects\Rinata\output" \
         "C:\Users\shant\projects\Rinata\prompts"

Breaking it down:

  • mkdir — "make directory." Creates a folder.
  • -p — "parents." Creates nested folders in one shot, and doesn't error if they already exist. Without -p, you'd have to create each folder one at a time.
  • Multiple paths listed — creates all four folders in a single command instead of four separate commands.

Step 2 — Installing Python Libraries

What we did

We installed five Python packages that the project will depend on throughout all six stages.

python3 -m pip install playwright anthropic openpyxl pandas python-dotenv

What is pip?

pip is Python's package manager — it downloads and installs code libraries written by other developers so you don't have to write everything from scratch. Think of it like an app store, but for Python code.

We used python3 -m pip instead of just pip because on Windows, calling pip directly sometimes points to the wrong Python installation. Using python3 -m pip guarantees we're using the pip that belongs to our specific Python version.

Installing the Playwright browser

python3 -m playwright install chromium

Playwright is a two-part install:

  1. The Python library — installed with pip above. This is the code that controls the browser.
  2. The browser itself — Playwright downloads a specific version of Chromium (the open-source engine behind Google Chrome) that it knows how to control reliably. This is separate from your regular Chrome browser.

We chose Chromium (not Firefox or WebKit) because Google Maps is optimized for Chrome-based browsers.

Concept: What is an SDK?
SDK stands for Software Development Kit. When a company (like Anthropic) offers an API, they often publish an SDK — a library that wraps the raw API calls in clean, easy-to-use Python functions. Without the anthropic SDK, you'd have to manually write HTTP requests with headers, handle errors, parse JSON responses, etc. The SDK handles all of that for you.

Step 3 — Creating the .env File

What we did

We created a file called .env in the project root containing one line:

ANTHROPIC_API_KEY=sk-ant-api03-...

What is a .env file?

A .env file (pronounced "dot env") is a plain text file used to store environment variables — values that your program needs to run but that should never be hardcoded into your scripts.

The classic example is an API key. If you write your key directly in your Python script like this:

# BAD — never do this
client = anthropic.Anthropic(api_key="sk-ant-api03-...")

...and then share that script with anyone, or put it on GitHub, your key is exposed and anyone can use your API account and bill you. A .env file keeps the key separate from the code.

What is an API Key?

An API key is like a password + identity card combined. When your script sends a request to Anthropic's servers, the key tells them:

  1. Who you are — which account is making the request
  2. That you're authorized — the key proves you have permission
  3. How to bill you — usage is tracked and billed per key

API keys should be treated like passwords: never share them, never commit them to version control, and rotate them if you accidentally expose one.

Security note: Your API key was shared in plain text during this session. It is recommended to rotate it at console.anthropic.com — go to API Keys, revoke the current one, and generate a new one. Then update the value in your .env file.

What is an environment variable?

An environment variable is a named value stored in the operating system's memory, accessible to any program running in that environment. Programs can read these values at runtime without them being baked into the code itself.

Think of it like a bulletin board in a kitchen — the chef (your Python script) reads the specials (variables) posted there rather than having them printed permanently in the recipe book (source code). The specials can change without reprinting the book.

The format in a .env file is always: VARIABLE_NAME=value — all caps for the name by convention, no spaces around the =.

Step 4 — Writing the Test Script

What we did

We created test_api.py — a short script that reads the API key from the .env file, connects to Claude, and prints a confirmation message.

The full script with line-by-line explanation

from dotenv import dotenv_values   # 1
from pathlib import Path              # 2
import anthropic                       # 3

env = dotenv_values(                    # 4
    Path(__file__).parent / ".env"     # 5
)

client = anthropic.Anthropic(           # 6
    api_key=env["ANTHROPIC_API_KEY"]   # 7
)

message = client.messages.create(       # 8
    model="claude-haiku-4-5-20251001", # 9
    max_tokens=64,                     # 10
    messages=[{                         # 11
        "role": "user",
        "content": "Say 'Rinata API connection successful!' and nothing else."
    }]
)

print(message.content[0].text)        # 12

Line-by-line breakdown:

  1. Line 1: Imports dotenv_values from the python-dotenv library. This function reads a .env file and returns its contents as a Python dictionary.
  2. Line 2: Imports Path from Python's built-in pathlib module. Path objects represent file system paths in a cross-platform way (works on Windows, Mac, and Linux).
  3. Line 3: Imports the anthropic library — the Claude API SDK.
  4. Line 4: Calls dotenv_values() and stores the result in a variable called env. The result is a dictionary like {"ANTHROPIC_API_KEY": "sk-ant-..."}.
  5. Line 5: Path(__file__) is the path to the current script file. .parent gives us the folder that contains it (the Rinata/ directory). / ".env" appends .env to that path. This means the script always finds the .env file relative to itself, no matter where you run it from.
  6. Line 6: Creates an Anthropic client object — the thing that knows how to communicate with Claude's API.
  7. Line 7: Passes the API key from our env dictionary into the client so it can authenticate.
  8. Line 8: Calls client.messages.create() — this is the actual API call that sends a message to Claude and waits for a response.
  9. Line 9: Specifies which Claude model to use. We chose claude-haiku — the fastest and cheapest model, perfect for a quick test.
  10. Line 10: max_tokens=64 limits how long Claude's response can be. A "token" is roughly 0.75 words. 64 tokens ≈ about 48 words — plenty for a short confirmation message, and prevents accidentally generating (and being billed for) a long response.
  11. Line 11: The messages parameter takes a list of message objects. Each has a role (either "user" or "assistant") and content (the text). This mirrors a conversation format — you always need at least one user message to get a response.
  12. Line 12: Prints Claude's response. message.content is a list (Claude can return multiple content blocks). [0] gets the first one. .text extracts the actual text string.

Debugging We Encountered (and What We Learned)

Problem: load_dotenv() wasn't loading the key

Our first version of the test script used load_dotenv() which is the standard approach. It loads the .env file and injects the values into the operating system's environment variables. The script would then read them with os.getenv("ANTHROPIC_API_KEY").

But os.getenv() returned None — the key wasn't there.

Why it happened:

The shell (the terminal environment) already had ANTHROPIC_API_KEY set — possibly to an empty string "". By default, load_dotenv() does not override existing environment variables. So it saw a value already existed and skipped it.

How we diagnosed it:

We ran three diagnostic commands:

# Test 1: Does dotenv parse the file correctly?
dotenv_values(".env")
# Result: returned the key correctly ✅

# Test 2: Does load_dotenv set the env var?
load_dotenv(); os.getenv("ANTHROPIC_API_KEY")
# Result: returned None ❌

# Test 3: Is the key already in the environment?
os.getenv("ANTHROPIC_API_KEY", "NOT SET")
# Result: empty string — the variable existed but was blank

How we fixed it:

Instead of using load_dotenv() + os.getenv(), we switched to dotenv_values() which reads the .env file and returns a plain Python dictionary — it never touches the OS environment variables at all. We then pass the value directly where needed.

# Fixed approach — reads file directly, ignores OS environment
env = dotenv_values(Path(__file__).parent / ".env")
client = anthropic.Anthropic(api_key=env["ANTHROPIC_API_KEY"])
Key lesson: Debugging is normal. The systematic approach — isolate each part, test each part independently, identify where the chain breaks — is more important than knowing the answer upfront. This three-step diagnostic process is exactly how experienced developers debug.
