What Is Web Scraping?

Web scraping is the process of writing code that controls a web browser or sends HTTP requests to a website, reads the content of the page, and extracts structured data from it — automatically, at scale.

Think of it like having a very fast assistant who opens a browser, scrolls through hundreds of reviews, copies each one into a spreadsheet, and sends it to you — except the "assistant" is your Python script.

When scraping is appropriate:

  • The data is publicly visible on the website
  • No official API exists (or the API is too limited)
  • You own or have a legitimate interest in the business being reviewed
  • You're not overloading the server with requests
Key concept — Static vs. Dynamic pages:
Old websites sent the full HTML content when you loaded a page. Modern websites like Google Maps load a basic shell and then fill in the content using JavaScript after the page loads. This is why simple HTTP request scrapers don't work on Google Maps — you need a real browser that can execute JavaScript.

What Is Playwright?

Playwright is a library developed by Microsoft that lets you control a real web browser from Python code. It can launch Chrome, Firefox, or WebKit (Safari's engine), navigate to URLs, click buttons, scroll pages, fill out forms, take screenshots, and read page content — all programmatically.

The two modes we used:

ModeWhat it meansWhen to use
Headful (headless=False)A visible browser window opens — you can watch it workDebugging, learning, when you need to log in manually
Headless (headless=True)The browser runs invisibly in the backgroundProduction automation, faster, no screen needed

We used headful mode throughout Stage 2 so you could see exactly what the scraper was doing — this is best practice when building and debugging a new scraper.

Core Playwright pattern

from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch(headless=False)
    context = browser.new_context(viewport={"width": 1280, "height": 900})
    page = context.new_page()

    page.goto("https://www.google.com/maps/...")
    page.locator('button[aria-label*="Reviews"]').first.click()
    text = page.locator(".wiI7pd").first.inner_text()

    browser.close()

Date Parsing — Converting "3 weeks ago" to a Real Date

Google Maps doesn't show exact review dates — it shows relative strings like "2 weeks ago", "a month ago", "3 years ago". To do day-of-week analysis, we need to convert these to approximate calendar dates.

The parse_relative_date() function

def parse_relative_date(text):
    today = datetime.today()
    text = text.lower().strip()

    # "just now", "5 minutes ago", "2 hours ago" → today
    if not text or "just now" in text or "minute" in text:
        return today

    # Match "3 weeks ago" or "a month ago"
    n_match = re.search(r"(\d+)\s*(day|week|month|year)", text)
    a_match = re.search(r"\ba\s+(day|week|month|year)", text)

    if n_match:
        n, unit = int(n_match.group(1)), n_match.group(2)
    elif a_match:
        n, unit = 1, a_match.group(1)   # "a week ago" = 1 week
    else:
        return today

    if unit == "week":
        return today - timedelta(weeks=n)
    elif unit == "month":
        return today - timedelta(days=n * 30)
    elif unit == "year":
        return today - timedelta(days=n * 365)

Concepts used:

  • Regular expressions (regex): re.search(r"(\d+)\s*(week|month|year)", text) — a pattern that finds a number followed by a time unit. The (\d+) captures one or more digits. The \s* matches zero or more spaces.
  • timedelta: A Python object representing a duration of time. timedelta(weeks=3) is 3 weeks. Subtracting it from today's date gives you the approximate review date.
  • Approximation: "a month ago" is treated as 30 days. This introduces a small error but is acceptable for day-of-week analysis — we care whether a complaint happened on a Friday, not the exact date.

How the Scrolling Works

Google Maps uses lazy loading — it only renders review cards as you scroll down. The page doesn't load all 597 reviews at once because that would make the page very slow. Instead, it loads ~10 at a time as you reach the bottom.

Our scraper replicates this by repeatedly scrolling the reviews panel to its bottom, waiting 2 seconds for new cards to load, and counting how many cards are now on the page. When the count stops increasing for 5 consecutive scrolls, we know we've reached the end.

The scroll loop

for attempt in range(100):
    count = page.locator("div.jftiEf").count()

    if count != last_count:
        print(f"  Reviews loaded: {count}")
        stale = 0
        last_count = count
    else:
        stale += 1
        if stale >= 5:     # 5 scrolls with no new reviews → done
            break

    panel.evaluate("el => el.scrollTo(0, el.scrollHeight)")
    time.sleep(2)      # wait for Google to load more cards
Key concept — element.evaluate():
This runs a JavaScript snippet directly inside the browser. el.scrollTo(0, el.scrollHeight) is JavaScript that scrolls an element to its very bottom. Sometimes you need to drop into JavaScript when Playwright's Python API doesn't have a direct method for what you need. This is a common pattern in browser automation.

The Anti-Scraping Problem — What We Hit and How We Solved It

This was the most educational part of Stage 2. We hit three different blocking mechanisms, diagnosed each one, and found a solution. Real-world scraping almost always involves this kind of debugging.

Blocker 1

Google's "Limited View" for unauthenticated users

What happened: Every time we launched a fresh Playwright browser and navigated to Google Maps, the page showed only "Overview" and "About" tabs — no Reviews tab. A message at the bottom read "You're seeing a limited view of Google Maps."

Google detects when a browser session has no login cookies and intentionally withholds content, including reviews. This is a common pattern — many sites give logged-in users more content than anonymous visitors.

Solution: Instead of fighting the restriction, we changed the approach entirely. We launch a visible browser, navigate to accounts.google.com, and pause to let you log in manually. After you press Enter, the session has your Google cookies and Maps shows the full authenticated view — including all Reviews, Menu, and About tabs.
Concept — Browser sessions and cookies:
When you log into a website, the server gives your browser a small piece of data called a cookie. Your browser sends this cookie back with every future request, proving you're logged in. A fresh Playwright browser has no cookies — it's like opening an incognito window. By logging in manually within the Playwright session, we populate it with the right cookies.
Blocker 2

Chrome profile lock — launch_persistent_context hang

What happened: We tried to use your existing Chrome profile (where you're already logged into Google) to skip the manual login step. The script called launch_persistent_context(user_data_dir=...). Chrome launched — but then hung indefinitely at context.new_page().

The root cause: launch_persistent_context automatically opens one page when it launches. Calling new_page() on top of that created a conflict. The fix was to use context.pages[0] instead — but the deeper problem was that the Chrome profile's cookie database file was locked by the running Chrome browser, causing incomplete profile copy issues.

Solution: Abandoned the profile approach. The manual login approach (Blocker 1's solution) was simpler and more reliable.
Concept — File locking:
When Chrome is open, it keeps exclusive lock on its profile database files (like the Cookies file). No other process can read or write those files while Chrome holds the lock. This is why copying the profile while Chrome is open either fails or produces a corrupt copy.
Blocker 3

Extraction hung on 300 reviews — click_more_buttons bottleneck

What happened: The scraper successfully loaded 300 reviews and then went completely silent. No output for many minutes. The terminal showed "Reviews loaded: 300" as the last line.

The cause: inside the scroll loop, we were calling click_more_buttons() on every scroll pass. This function searched for every "More" button on the page and checked is_visible(timeout=300ms) on each one. With 300 review cards, that's up to 90 seconds of visibility checks per scroll pass — completely blocking progress.

Solution: Removed click_more_buttons() from the scroll loop entirely, and simplified the extraction to just read whatever text was already visible. This cut extraction time from "never finishing" to under a minute.
Concept — Performance profiling intuition:
When a script hangs with no output, the question is always: "what is it doing right now?" The last printed line tells you where you are in the code. Working backwards from "Reviews loaded: 300", we knew we had entered the scroll loop's next iteration. The only slow operation there was click_more_buttons(). This is basic performance debugging — identify the last known state, then look at what runs next.

The extraction loop — reading each review card

for i, card in enumerate(cards):
    rating  = extract_rating(card)           # reads aria-label="5 stars"
    date_raw = extract_text(card, [".rsqaWe"])  # "3 weeks ago"
    review_text = extract_text(card, [".wiI7pd"]) # full review text
    has_response = card.locator(".CDe7pd").count() > 0

    review_date = parse_relative_date(date_raw)  # → datetime object

    reviews.append({
        "reviewer_id": f"Reviewer_{i+1:03d}",   # zero-padded: 001, 002...
        "rating": rating,
        "date_raw": date_raw,
        "date_approx": review_date.strftime("%Y-%m-%d"),
        "day_of_week": review_date.strftime("%A"),  # "Monday", "Friday"...
        "review_text": review_text,
        "has_owner_response": has_response,
    })
Concepts used:
enumerate() — iterates a list and gives you both the index (i) and the item (card) simultaneously.
strftime() — formats a datetime object as a string. "%Y-%m-%d" = "2026-04-20". "%A" = "Monday".
f-string with format spec: f"Reviewer_{i+1:03d}" — the :03d means "format as an integer with at least 3 digits, zero-padded." So 1 → "001", 42 → "042".
