Overview

Executive Summary

The Rinata AI Agent Suite is a collection of purpose-built Python agents that automate the highest-friction, most repetitive operational tasks at Rinata restaurant. Each build is a standalone pipeline that ingests real restaurant data, processes it through Claude (Anthropic's AI), and outputs a ready-to-use deliverable — an Excel workbook, a response draft, or a priority queue — that the manager can act on in minutes rather than hours.

The suite runs on a thin harness / fat skills architecture: 85% deterministic Python code handles data ingestion, cleaning, and formatting; Claude handles only the judgment calls (categorization, tone, summarization). This makes the system fast, auditable, and cheap to operate.

Three builds are complete as of this report. Together they cover guest review intelligence, owner response drafting, and supplier email triage — eliminating an estimated 6–10 hours of weekly manual work.

Email Categories

Category Description Urgency Example
price_change Vendor announcing price increases or decreases on any item Always High "Chicken breast pricing update effective June 1"
dispute Wrong items, shortages, damaged goods, billing errors Always High "Short shipment on your June 3 order — 2 cases missing"

promo Vendor marketing, sales promotions, product announcements Low "Summer specials — 10% off seasonal produce this week"
general Anything else: introductions, relationship emails, miscellaneous Low "Introducing your new account rep, Maria Johnson"

Output Workbook — 4 Sheets

Sheet 1 — All Emails

Full list of all supplier emails, colour-coded by urgency (red = high, amber = medium, green = low). Sortable and filterable. Every email includes: date, supplier name, subject, category, urgency, one-sentence summary, and a plain-English action item.

Sheet 2 — Urgent Queue

High-urgency emails only, sorted with price changes and disputes at the top. This is the first thing to check each morning. Price changes need a decision; disputes need a call.

Sheet 3 — Invoices

All invoice emails in one place for accounts payable. Each row includes the extracted amount, due date, and invoice number where available.

Sheet 4 — Price Changes

Price change notices isolated for review. These are the emails that compound silently — a 5% increase on chicken breast adds up to thousands of dollars a year if missed.

Build 6 — Setup & Usage

Getting Build 6 Running

Prerequisites

You need the restaurant's Google Workspace login credentials and access to create a Google Cloud project under that account. This setup takes about 10 minutes and only needs to be done once.

One-Time Setup — Google Cloud Console

1

Sign in to Google Cloud Console

Go to console.cloud.google.com and sign in with the restaurant's Google Workspace account (not your personal Gmail). Create a new project — name it "Rinata Agents" or similar.

2

Enable the Gmail API

In the left sidebar: APIs & Services → Library. Search for "Gmail API" and click Enable.

3

Create OAuth 2.0 Credentials

Go to APIs & Services → Credentials → Create Credentials → OAuth 2.0 Client ID. Choose Desktop app as the application type. Name it anything. Click Create.

4

Download credentials.json

Click the download icon next to the credential you just created. Save the file as credentials.json and place it at:

C:\Users\shant\projects\Rinata\email_triage\credentials.json
5

Configure Your Suppliers

Open email_triage/suppliers.json and add the restaurant's actual supplier email domains. The file already has Sysco, US Foods, and Gordon Food Service as examples — update with whoever actually delivers to Rinata.

// Example entry — add your actual suppliers { "name": "Local Produce Co", "domains": ["localproduceco.com"], "category": "Produce" }
6

Authenticate (browser opens once)

Run the auth script from your terminal. A browser window will open — sign in with the restaurant's Google account and grant permission. This creates token.json and you won't need to do this again.

python email_triage/gmail_auth.py # Expected output: "✓ Authenticated as: rinata@..."

Running the Pipeline

Full run (fetch new emails + categorize + build workbook)

python email_triage/run_email_triage.py

Fetch last 7 days only

python email_triage/run_email_triage.py --days 7

Re-categorize without fetching (useful after editing the prompt)

python email_triage/run_email_triage.py --skip-fetch

Smoke test — categorize only 5 emails

python email_triage/categorize_emails.py 5

Idempotency

Every script is safe to re-run. Emails already fetched or categorized are skipped automatically — you'll never pay twice to process the same message.

Recommended Cadence

Run run_email_triage.py every weekday morning before the manager arrives. Takes under 2 minutes. Open Rinata_Email_Triage.xlsx → Sheet 2 (Urgent Queue) first, then Sheet 3 (Invoices) for payment review.

Build 2 Hardening & Approval Automation

This addendum records work completed after Build 2's initial sign-off. The agent was production-hardened, gated behind an owner approval step, and wired for unattended scheduling. The architecture principles are unchanged — deterministic Python does the work, Claude is used only for the response wording, and every run stays auditable and cheap to operate.

What Was Added to Build 2

Enhancement What it does Why it matters
3★-and-below filter Drafts replies only for reviews rated 3 stars or lower. Ownership only responds to critical and negative feedback. Cuts the working set from 386 reviews to 32, drops API cost to near-zero, and focuses attention where it counts.
Pipeline orchestrator
run_all.py		 One command runs clean → categorize → workbook → responses → sheets in the required order, with sanity checks between steps. Makes the suite safe to schedule unattended. Aborts if the scraper returns suspicious data instead of letting it flow downstream, and enforces step order so the response sheets are never overwritten.
Idempotent reruns Skips reviews already approved or rejected; carries still-pending drafts forward unchanged. Re-running never duplicates work, never rewrites a draft the owner is mid-review on, and never pays the Claude API twice — the same idempotency standard as Build 6.
Approval workflow Every draft is held as "Pending Review" until the owner explicitly approves or rejects it. No AI-written text reaches a public Google review without a human decision.

Docker-aware design

Because n8n runs inside Docker — isolated from the host's Python, files, and Chrome — the workflow uses a file-handoff design over a mounted volume rather than calling host commands. The host runs the pipeline on a schedule; n8n only sends the approval emails and writes decisions back into the shared output/ folder. n8n stays a thin orchestrator, and no Python or browser has to live in the container.

Honest limitation — no auto-posting

Build 1 scrapes Google reviews; it cannot post replies. "Approved" means a clean, owner-approved list (approved_responses.csv) the manager pastes into Google Business Profile. True auto-posting would require the Google Business Profile API and is deliberately out of scope — AI text is never published unattended.

Addendum — Infrastructure

Infrastructure & Tooling Decisions

Two infrastructure items were addressed alongside the Build 2 work. Both are recorded here with their rationale so the decisions are not revisited without cause.

GitHub MCP Server — Connected

The official GitHub MCP server was connected to Claude Code via Docker and registered at user scope, so it is available in every future session. This lets the assistant read pull requests and repository state directly during development work.

docker run -i --rm -e GITHUB_PERSONAL_ACCESS_TOKEN ghcr.io/github/github-mcp-server # Status: ✓ Connected — verified via `claude mcp list`

Local Models — Evaluated & Declined

Docker Model Runner was enabled and smoke-tested with a small local model. It works, but CPU-class local models are far weaker at instruction-following — directly at odds with this suite's governing principle: accuracy over speed, because this is financial data (most critical for Builds 3 & 4). The Claude API costs under a dollar for the entire review set.

Decision — the suite stays on the Claude API

Docker Model Runner remains installed but idle. Local inference will be reconsidered only if a hard data-residency requirement appears (financial data contractually cannot leave the machine) — and even then with a properly-sized GPU model, not a small CPU one.
